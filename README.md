# x14 - "X14" (Orange, 1995, winner of Juhla 2)

Code Hoplite, music Dune (`X14.S3M`), graphics Der Piipo. Original files untouched.

**Status: all 13 effects are ported to JS and run in the browser.** all but fx4 are checked exact against the Unicorn run of the original in the table's sense (fx4: 357 of 547 records, see below). The detailed evidence is in `re/NOTES.md`.

## Files

- `X14.EXE`: 130 KB, a PKLITE real-mode 386 program that switches itself to 32-bit protected mode with its own extender.
- `DATA.DAT`: 932 KB, blobs read by absolute or from-the-end offsets.
- `X14.S3M`, `INFOFILE`, `FILE_ID.DIZ`. Needs a 386+, GUS optional.
- `AO070295.EXE`: copy of an unrelated small executable, not analysed.

## Run and test

```
cd web && python3 -m http.server 8000
node web/test-player.mjs
node tools/uitest.mjs                    # headless Chrome: play/pause/seek on all 13 effects
node tools/fxcheck.mjs FX PREFIX         # diff against the oracle
node tools/schedcheck.mjs FX PREFIX      # fx0/fx1 player schedule
```

## Approximated or unresolved

- **Entry times** of all effects (`entries.js`) and the vsync phase are harness measurements, not derived. On real hardware they depend on CPU and disk.
- **Music clock** is libopenmpt's. The oracle check used the harness' own S3M model, which differs by 0.07 %.
- **One tick and one pass per vsync.** The port assumes it. The harness (Unicorn at 12 MIPS) needs 2 to 3 vsyncs per pass, so its per-pass state differs, mainly in fx4, 5, 7, 8, 9, 10 and 11. Whether a 1995 CPU met the condition per effect cannot be derived.
- **fx0 and fx1 schedules are fitted** to the harness (`web/fx/sched.js`, generated by `tools/mk_sched.py`). The pass cost depends on the CPU. The fill counts for fx1 are read from the original, but whether a tick fell between two reads is replayed, not predicted.
- **Harness limits:** IRQ0 is injected between 2000-instruction chunks, not per instruction. The CRTC line-compare split was added to the harness display and is not validated on an original frame.
- **Not modelled:** the grey palette flash after the exit.
- **Oracle dumps used instead of generators:** fx1's warp map, texture, LUT and initial buffer; fx0's 64 KB LUT window and texture colour tables.

## dosbox-x comparison (21 Nov 2026)

Screenshots of the unmodified original (2 s steps) against the port, same window position, max channel diff 1 = 6 to 8 bit DAC rounding.

| Effect | Result |
|---|---|
| fx3, fx6, fx12 | pixel-exact over the full frame (fx12 confirms the mode 12h VRAM clear) |
| fx9 | unwritten rows 0-47 and 348-399 are palette[0] in both |
| fx0, 1, 2, 4, 5, 7, 8, 10, 11 | blank bands, borders and edges at the same places |
| fx1 | normal data in rows >= 332 and the x&2 planes: the old "lost writes" were a harness artifact |

Mode sets: the original does int 10h mode 13h (fx0, 2, 4-11) and 12h (fx12), never with AL bit 7, so VRAM is always cleared; fx1 and fx3 inherit the mode. The harness now reloads the BIOS default DAC at each mode set (`re/emu.py default_dac()`). An audit (`AUDIT=1`, `re/oracleA/audit.json`) shows every effect fx0-fx12 writes all 256 DAC entries after its mode set and displays no unwritten index, so the reload changes nothing for them (only the intro uses an unwritten index 0, black by default). The default table itself is not checked against dosbox-x.

Limits: only the stable middle sections were compared, and the 0.6-1.2 s video/music offset below is unexplained.

## Refresh rates (dosbox-x cross-check, 20 Nov 2026)

The timer is a PLL locked to the retrace, so an effect's tick rate is its own refresh rate, independent of the CPU.

- **449-line modes** (fx0, 1, 4-7, 9, 11): 70.086 Hz.
- **527-line modes** (fx2, 3, 8, 10, CRTC regs 6/7 = 0x0d/0x3e): 59.714 Hz. Fades are counted in ticks, so they stretch (the fx3 fade lasts 1.07 s, not 0.91 s).
- `web/fx/common.js vsync(fx)` applies this, and the harness takes the refresh from the live CRTC (`re/emu.py refresh_hz()`).
- Verified from the original's own writes over the whole demo: misc output 0x63 (449 lines) or 0xe3 (527 lines), 25.175 MHz, 8-dot clocking.
- **Unresolved:** in dosbox-x the video runs ahead of the port by 0.6 to 1.2 s in fx3 to fx11. It is the same for max cycles and 12 MIPS, and the rate fix does not change it.

## Display options

The "RGB pixels" button (key R) merges the R, G, B scanline triplets of fx0 and fx1 into true RGB pixels. For fx11 it also un-dithers the text and column layers, and for fx12 it applies a 3x3 [1 2 1] smoothing to remove the 16-colour dither. The default is the original interlaced look.

## End of the demo

- fx12 never ends in the original. It ends with `cmpw $0x3b,[0x3575]; jne`, but with the GUS player both bytes hold the order, so the word compared is 0x3b3b and never 0x3b. There is no key check either.
- The music loops to order 0 after order 62.
- The port keeps the final picture on screen and stops at the end of the S3M (250.4 s) instead of looping.

- **The top 40 lines of the final screen are black, no white pixels.** (An earlier revision of this port showed white fx11-text leftovers there and claimed it was faithful: wrong.) fx12 does set a BIOS mode: its first instructions put 0x12 in [0xe0] and call the extender's int 33h gate (int 10h ax=0012, flat 0x7aba4), which clears all four planes; plane 0 is therefore 0 outside the picture, exactly like planes 1-3 are 1 (colour 14 = black). The unmodified original in dosbox-x shows the same (top 120 screenshot rows all black at 224-250 s).
